Top note — will this help, or could it hurt?

EXTRACTION items make numbers more correct (raise accuracy); VALIDATION items detect wrong numbers but don't fix them (raise trust, not the count of correct values). Net OpenAI cost across all items is flat or lower. But several items can degrade accuracy or pipeline time if adopted as a replacement or a hard gate (see Risk column). The rule: augment, don't replace; advisory before gating; keep the face-truth override as a floor; A/B every change against the current outputs.

Bottom note — quick read & safe-adoption rule

  • Safe (Low risk), do first: rows 1–4 (4 as advisory), 13, 17, 19–25, 28 — additive/detection, change no existing numbers, ~no time cost.
  • Genuine accuracy levers (Med risk), pilot & measure: rows 5–12, 14–16, 18, 22, 23, 26 — can help, but a wrong gate/ranking can regress; A/B each on both companies before keeping.
  • High risk — never blind cutover: #5 Camelot (loses scanned-page data, 3× slower) and #7 declared-basis gate (over-exclusion empties a statement) and #29 Table Transformer (heavy time/disk). Run behind the metric, augment-don't-replace.
  • The rule that prevents degradation: augment never replace; advisory before gating; keep the face-truth override as a floor (it's why headlines are correct today); A/B against current outputs using the detail_reconciliation metric + headline tie-out, and revert anything that lowers either number or raises pipeline time without a clear accuracy gain.
  • Prerequisite: the accounting validators are a no-op without a metric-alias dictionary (leaf label → canonical) tuned to our corpus.
